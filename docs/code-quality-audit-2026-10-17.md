## E. 残っている課題（優先順）

1. **依存の更新判断**：重大な指摘の到達性を調べ、SDK 57対応版・間接依存の修正方法を比較する。SDKやRNのダウングレードを伴う自動修復は使わない。更新後にカメラ・通知・共有・復元を端末で確認する。
2. **実機で例外系を確認**：通知からの終了状態・前面復帰時の起動、カメラ許可の拒否・再許可、保存の連打、写真を含むv1/v2復元と容量不足を確認する。
3. **保存容量と画像の整理**：Webの容量予告と、商品候補写真の安全な整理を別の小さな修正として設計する。現行世代・保持原本・商品・在庫の参照を壊さないことを条件にする。
4. **大量の記録での描画**：実機で在庫・統計履歴の件数別に計測し、必要なら日付索引・仮想化を導入する。
5. **保守とまれな境界条件の整理**：年1〜99の日付処理、不要候補の依存、通知の互換API、バージョン表示、OSS通知の未収集本文を個別に点検する。OSS通知の対象535パッケージ中、本文ありは474件という既存の集計で、全ライセンス確認済みとは扱わない。

## F. 今後の開発への提案

- 不具合は「通常の画面テスト」だけで終わらせず、連打・待機中のデータ変更・拒否・復元途中の失敗を最小の再現テストにしてから直す。今回追加したテストもこの方針で維持する。
- 在庫の一部だけを変える操作では、画面で保持していた食材全体を渡さず、変更する項目だけを最新レコードへ適用する。数量など競合の影響が大きい操作は既存のrevision・同一レコード確認を維持する。
- 保存・復元・削除の回帰テストを必須にしたまま、小さいPRで更新する。大きいContextの分割や保存先の変更は、計測・障害時の手順・互換性のテストを揃えてから行う。
- 依存診断とセキュリティ指摘の確認を定期的に行い、互換性検査と実際の攻撃経路の評価を分けて記録する。現行CIのテスト・型検査に加える場合も、外部サービス停止だけで開発が止まらない運用を設計する。

参照したSDK仕様：[Expo SDK 57](https://docs.expo.dev/versions/v57.0.0/)、[Notifications](https://docs.expo.dev/versions/v57.0.0/sdk/notifications/)、[Camera](https://docs.expo.dev/versions/v57.0.0/sdk/camera/)。実装は導入済みパッケージの型・ソースとも照合しました。
