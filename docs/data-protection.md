# データ保護と復旧（Phase 1）

## 利用者向け

- バックアップ復元は、画像と全データの保存を確認してから切り替えます。準備中の失敗では現在の保存先を変更しません。
- 復元中は他の在庫操作を止めます。完了するまでアプリを閉じずに待ってください。
- 保存データが読めない場合は、初期化せず「もう一度読み込む」「原本をファイルに退避」「バックアップから復元」を選べます。
- 原本の退避ファイルは調査・救出用です。通常のバックアップとは異なり、写真本体は含まず、通常の復元には使えません。在庫・メモ等の個人データを含むので安全な場所へ保存してください。
- 不正な日付・数量・重複IDなどは自動修正して上書きせず、読み込みを止めます。修復には正常なバックアップまたは退避した原本の調査が必要です。

## 画面の表示中にエラーが起きた場合

`AppErrorBoundary` がデータ用のProviderと画面遷移を囲み、子の描画・ライフサイクル中の例外を捕まえると「画面を表示できませんでした」を表示します。このエラー画面への切り替え自体は保存データを削除・初期化しません。保存前の入力内容は戻らない場合があります。

「もう一度表示する」でエラー状態を解除し、データと画面を読み込み直します。原因が残っていれば同じエラー画面へ戻ります。「保存データを書き出す」は既存の `shareRecoveryData` で端末内の原本を退避します。写真本体を含まない調査・救出用のファイルで、通常のバックアップ復元には使えません。Web版は既存のダウンロード処理、ネイティブ版は既存のファイル共有を使います。保存先でファイルが作成されたことを確認してください。利用不可や失敗は案内を表示し、再試行できます。書き出し中は二重操作と再表示を防ぎます。

アラートとトーストのProviderは境界の外に置きます。`componentDidCatch` はコンソールへの記録のみで、エラーを外部送信しません。詳細は開発時（`__DEV__`）だけ画面に表示します。イベント処理・通常の非同期処理・境界自身やその外側の例外、ネイティブのクラッシュはこの仕組みの対象外です。iOS／Androidの開発時は開発用エラー表示が重なる場合があるため、リリース相当のビルドでも確認が必要です。

## 保存方式

既存の `@food-manager/foods` などのキーは、最初の復元まではそのまま読み書きします。初回起動と、既知の旧データの補完・レシピ移行も維持します。

復元時は一つの保存キューで、次の処理を行います。

1. 待機中の通常保存を完了させ、復元前のキーと生のJSON文字列を `@food-manager/generation/<id>/original` に退避する。
2. 画像を新しいファイルに書き、サイズを確認する。Webでは検証したdata URIを保持する。
3. 食材・レシピ・買い物・通知設定・学習商品を、新しい世代の5キーへ保存して読み戻す。
4. 最後に `@food-manager/active-generation` の1キーだけを書き換える。
5. 以後の読み書きは、この参照先の世代に対して行う。

切り替え前に終了した場合は旧世代、切り替え後は新世代を読みます。参照先のデータが欠けた場合は、古いキーやサンプルへ勝手に戻さず復旧画面に進みます。

切り替えの書き込みがエラーを返した場合は実際の参照先を確認します。結果が判別できない場合は通常保存を止め、再読み込みを求めます。古い画面の状態を新しい世代へ上書きしません。

この方式はAsyncStorageの単一キー書き込みを確定点とします。キューは同じアプリ実行環境内の操作を直列化するもので、複数のブラウザータブや別プロセス間の排他制御ではありません。

旧アプリは世代キーを認識しません。この変更後に復元を行った端末を古いアプリへ戻すと、旧キーの古いデータが表示される可能性があるため、配布時のダウングレード手順には注意が必要です。

## 写真の保護

Reactのstate更新関数内では画像ファイルを削除しません。関連する通常保存がすべて成功した後で、現在の画面・保存データ・学習商品・退避した原本から参照されていない写真だけを削除します。削除に失敗しても保存は成功として扱い、次の保存時に整理を再試行します。

写真の準備中に復元が失敗した場合は、その試行で作ったファイルだけを片付けます。保存・切り替えの段階まで進んだ試行の画像は、結果が不確かな場合の消失を避けるため保持します。

復元の成功後（切り替えと操作世代の更新後）と、起動時の全データの読み込み・検証に成功した後に、同じ保存キューで古い世代を整理します。`RETAINED_GENERATIONS = 2` とし、現在の世代の全データと原本、それ以外で日時が最も新しい1世代の原本を保持します。現在以外の世代の通常データと、保持数を超えた原本は削除します。旧形式のキーは変更しません。

日時は世代IDの先頭の36進数から判定します。同じ日時の場合はID順で決めます。形式や日時を判別できない世代（全データ削除後の `cleared-...` も含む）は削除せず、現在の参照先を確認できない場合も整理しません。そのため、例外的な世代や削除失敗が残ると2世代を超えることがあります。経過日数による自動保持期限や容量表示は設けていません。

復元中・全データ削除中・復元結果が不確かな間は整理しません。通常データを原本より先に整理し、途中で削除に失敗したら警告を記録して次の機会に再試行します。整理の失敗だけで保存・復元を失敗扱いにはしません。保持を終えた原本だけが参照していた写真は、以後の通常の写真整理で削除対象になります。現在の記録、残している原本、日時不明の原本が参照する写真は引き続き保護します。

## 保存データの一括削除（2026-10-01追加）

設定と復旧画面に削除の確認を設けました。対象と対象外を表示し、「削除」と入力してから開始します。完了後は在庫・買い物が空、通知OFF、内蔵レシピが初期状態になります。デモ設定による在庫の再投入は行いません。

1. 削除開始を専用キーへ保存して読み戻す。確認できなければ、写真・通知・既存データの削除を開始しない。
2. 通知の処理キューを待ち、期限・テスト通知の予約、通知センターの該当表示を解除する。
3. アプリが管理する写真ファイル、一時バックアップ・原本JSONを削除する。写真の参照は現在の記録だけでなく退避した原本も調べる。アプリの保存領域の直下以外、写真ライブラリ、関係のないファイルは削除しない。
4. `@food-manager/` の現在・旧世代・原本・途中データ・商品候補などを削除し、無関係な保存キーを残す。空の新しい保存先を作成して読み戻す。
5. 最後に削除開始のキーを取り除き、完了を確認する。

途中の失敗では開始記録を残します。再起動後も通常の読み込み・保存・復元を止め、削除の再試行だけを案内します。部分削除後の取り消しや、元の在庫への自動復帰は行いません。削除が成功したときだけ完了を表示します。

古いキューの保存・編集操作・準備済みバックアップには処理世代の検査を追加しました。別タブで参照先が変わった場合も古い書き込みを拒否します。ただしブラウザータブ／プロセス間の完全な排他制御ではないため、Webでは他のタブを閉じてから削除します。

写真ライブラリの元画像、外部へ保存したバックアップ、共有商品DB、OS・SDK管理のキャッシュ、OSのバックアップ、端末の権限は対象外です。媒体の復旧不能な上書き消去を保証する機能ではありません。ネイティブの写真・通知・容量不足・途中終了はAPIのモックで検証し、実機確認は残ります。
