# 公開前の権利・利用規約・プライバシー確認

[READMEへ戻る](../README.md)

確認日：2026-09-30。対象：コミット `cc89ff9` のアプリ・共有API・依存関係・配布設定。日本向けのWeb公開、App Store／Google Play配布を想定した技術面からの一次確認です。法律専門家による適法性の保証、ストアの審査承認、全世界の法令確認ではありません。

利用者からの回答：広告・課金の予定、アイコン／内蔵レシピ画像・文章の入手元はいずれも不明。したがって、それらを許諾済み・非商用・自作とは扱いません。アプリの機能やデータは変更せず、確認結果のみ追加しています。

## 結論と優先順位

現状のままで公開条件を満たしたとは判定できません。以下はすべてが「違法」という意味ではありません。規約への対応不足、著作権の確認不足、ストア審査上の問題を区別しています。

| 優先 | 項目 | 判定 | 公開前の対応 |
| --- | --- | --- | --- |
| 高 | プライバシーポリシー・問い合わせ先 | アプリ内に未実装。ストア要件に不足 | 運営者・通信先・保持／削除・連絡先を確定し公開、アプリからリンク |
| 高 | Open Food Factsの商品情報・画像 | ライセンス表示と出典の保持が不足 | データ／画像の出典・ライセンス・必要な著作者表示を整備 |
| 高 | 共有商品DBの投稿管理 | 公開時にUGC規定への対応が不足 | 投稿ルールへの同意、通報、審査・非表示、悪用者への措置、連絡先 |
| 高 | 同梱画像・文章の権利 | 入手元・許諾が未確認 | 素材ごとに制作元・ライセンスを記録。不明な素材は権利確認できるものに差し替え |
| 高 | Yahoo API | クレジット未対応、用途とIDの扱いが未解決 | 表示整備、利用範囲の判断、実運用IDを確認、必要なら公開版で停止 |
| 中 | OSS・フォントのライセンス | 配布物に必要な通知を網羅できていない | 最終配布物の依存一覧と著作権／ライセンス文を同梱 |
| 中 | 不要なマイク権限 | Expoの生成設定で存在を確認 | 不要な宣言を除去し、実際のリリースビルドを再確認 |
| 中 | 「完全に削除」と退避データ | 表示と保持範囲の不一致 | 削除範囲を説明し、退避・学習・写真の保持期限と消去方法を設計 |
| 未確定 | 商標、収益化、公開国、配布申告 | 判定材料不足 | 公開形態が決まった段階で追加確認 |

## 1. プライバシーポリシーと実際の外部通信

`SettingsScreen.tsx` にポリシー・運営者の問い合わせ先への導線がなく、リポジトリにも公開用ポリシーがありません。Apple 5.1.1とGoogle Playはアプリ内およびストア側のポリシー掲載を求めています。端末保存中心でも免除されるわけではありません。[Apple](https://developer.apple.com/app-store/review/guidelines/#privacy)、[Google Play](https://support.google.com/googleplay/android-developer/answer/10144311?hl=ja)

実装上、説明すべき通信は次のとおりです。

| 操作 | 通信先・情報 |
| --- | --- |
| バーコード検索 | 設定された共有API、Yahoo、Open Food Factsにバーコード。実際の経路はローカル候補の有無で変化 |
| 外部画像の表示 | Unsplashや商品画像の配信元へ画像リクエスト。通信先は接続元IPなどを受け取り得る |
| 商品情報の共有 | 共有APIへバーコード・商品名・分類・カテゴリ。自由入力欄に個人情報が書かれる可能性は残る |
| クックパッド検索 | 確認後にブラウザーへ食材の検索語を渡す |
| バックアップ | JSONに在庫・メモ・写真等を含め、利用者が保存／共有先を選ぶ。アプリ独自の暗号化なし |

共有APIは接続元IPから一時的なHMACを作ってレート制限します。DBには投稿者IDを保存しませんが、公開ホスト／プロキシのログや保持期間は未設定です。「個人在庫を共有しない」は実装で確認できますが、「外部送信ゼロ」「個人情報を一切扱わない」とは表示できません。

日本の個人情報保護法の適用は、運営者が実際に取得する情報、他情報との照合可能性、利用方法等によります。IPや商品名を一律に個人情報と断定していません。個人情報を取得する場合の利用目的通知・公表等は別途整える必要があります。[個人情報保護委員会](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)

App Privacy／Data safetyの申告状況は管理画面未確認です。第三者SDKやログも含め、実際のリリースビルドと公開サーバーに基づいて記入してください。[Apple申告](https://developer.apple.com/app-store/app-privacy-details/)、[Google申告](https://support.google.com/googleplay/android-developer/answer/10787469?hl=ja)

## 2. Open Food Facts：無料でも条件がある

`src/services/productLookupService.ts` は商品名・分類・画像を取得し、登録時に食材および端末内の商品候補へ保存します。バーコード画面にサービス名の説明はありますが、データ／画像のライセンスへのリンク、必要な著作者情報、保存後も追える出典情報がありません。`FoodItem`／`BarcodeProduct` はこれらの情報を保持しません。

公式資料では、データベースはODbL、個々の内容はDatabase Contents License、商品画像はCC BY-SAです。ライセンスに沿った出典表示、改変時の扱い、データベースの再利用条件を実装に反映する必要があります。画像内の第三者の権利についても留保があります。[Open Food Factsの公式ライセンス案内](https://openfoodfacts.github.io/openfoodfacts-server/api/tutorials/license-be-on-the-legal-side/)、[CC BY-SA 3.0](https://creativecommons.org/licenses/by-sa/3.0/)

この条件からアプリのソースコードや個人の冷蔵庫全体を公開しなければならない、とは判断していません。派生DBを公開する場合の条件と、端末内での個人利用は分けて検討します。現状、外部取得商品を共有DBへ自動転載しない境界は維持されています。

User-Agentが旧バージョンの学習用表記で連絡先もないため、公式推奨のアプリ名・バージョン・連絡先に更新し、Webで実際に送信される識別方法も確認します。現在のAPI案内のレート制限に合わせた制御も必要です。[API案内](https://openfoodfacts.github.io/openfoodfacts-server/api/)

公式の利用条件本文とWikiは取得時にアクセス制限があり、全文確認できませんでした。細部は未確定です。ライセンス案内には再利用の相談先 `reuse@openfoodfacts.org` が記載されています。

## 3. 共有商品DBはユーザー投稿コンテンツ

商品名だけでも、ユーザーの投稿を別のユーザーが見られるため、Google PlayのUGC定義に該当する構成です。AppleにもUGC規定があります。[GoogleのUGC規定](https://support.google.com/googleplay/android-developer/answer/9876937?hl=ja)、[Apple 1.2](https://developer.apple.com/app-store/review/guidelines/#user-generated-content)

現状は共有の任意チェックと項目制限がありますが、禁止投稿を定めた規約への同意、アプリ内の通報、内容審査、投稿者の悪用防止、公開連絡先がありません。文字数・制御文字の検査やIP制限は内容の審査ではありません。管理者用の `server/admin.cjs hide` はありますが、利用者から報告を受ける導線と対応運用が不足しています。

投稿形態に合った管理方法を設計し、審査前の保留、通報からの非表示、悪用者への措置を用意します。アカウントを一律必須にするとの判断ではありません。実装・運用できるまでは公開版の共有機能を無効にする選択肢があります。

現在の共有先は未設定という既存資料に基づく状態であり、今回公開サーバーの運用状況は確認していません。未公開のローカル試作自体を、既にストア規定違反として扱うものではありません。

## 4. 画像・レシピ文章・アイコン

`assets/recipes/` の同梱JPEG8枚、各アプリアイコン、`sampleData.ts` の内蔵レシピ、`localRecipeSuggestionService.ts` の文章について、制作元や許諾を示す記録を確認できませんでした。ユーザー回答も不明です。転載と断定はできませんが、公開許諾を確認した扱いにもできません。

素材台帳に、元ページ・著作者・取得日・ライセンス・加工内容を残します。生成画像の場合は利用サービスと生成履歴、参照素材の有無を確認します。料理の発想や単なる事実と、創作性のある文章・写真の複製は区別します。[文化庁：他人の著作物の利用](https://www.bunka.go.jp/seisaku/chosakuken/seidokaisetsu/chosakukensha_fumei/)

Unsplashの固定画像URLは `foodImages.ts`、`recipeImages.ts`、サンプルデータ等にあります。通常ライセンスは商用利用を認め、クレジットは必須ではありません。したがって、クレジットがないだけで通常ライセンス違反とはしません。ただし、各画像の出所・適用ライセンスや写り込んだ商標／人物等の権利は未確認です。[Unsplash License](https://unsplash.com/license)

Unsplash APIを使って取得・連携した画像には、通常ライセンスと別にAPIのクレジット・ホットリンク等の条件があります。現行コードにUnsplash API呼び出しは見つかりませんでしたが、固定URLの取得経路は不明です。Unsplash+素材も通常ライセンスと混同しません。[APIガイド](https://unsplash.com/documentation#guidelines--crediting)

クックパッド機能は確認画面の後に検索ページを開く実装で、本文・画像の取得や転載処理は見つかりませんでした。内蔵レシピの文章の入手元が確認できたことを意味するものではありません。

## 5. Yahoo APIの追加確認事項

指定クレジットが未実装で、画像URLを在庫・端末内商品候補に継続保存します。用途が許可範囲に入るか未確定です。クレジット追加だけで、あらゆる用途が許可されるわけではありません。[ガイドライン](https://developer.yahoo.co.jp/guideline/)、[表示規定](https://developer.yahoo.co.jp/attribution/)

`.env.example` に具体的なClient ID値があり、`EXPO_PUBLIC_YAHOO_SHOPPING_APP_ID` としてクライアントから直接使用します。公式のアプリケーション管理ページはIDの第三者への開示を避けるよう案内しています。READMEの「公開設定」という技術的説明だけではこの条件への対応になりません。IDの所有者・用途を確認し、例示値を除去、必要なら管理者側で再発行し、サーバー中継などで配布物から除く設計を検討します。Client IDを秘密鍵と同一視してはいません。[アプリケーション管理](https://e.developer.yahoo.co.jp/)

商用利用や画像利用の適合性は未解決です。また、公式お問い合わせページはショッピングAPIについて商用利用等の相談窓口を提供していない旨を記載しています。問い合わせれば必ず許諾が得られるとは案内しません。[問い合わせ案内](https://developer.yahoo.co.jp/developer/contact/)

## 6. OSSの著作権表示・ライセンス文

ルートのLICENSEはExpoのMIT通知です。これだけで全依存ライブラリや画像・データの条件を満たすとは限りません。React、React Native、Expo、アイコン／フォント等の配布対象について、著作権表示・ライセンス全文を集め、最終配布物に含める必要があります。表示画面は利用者が確認しやすくする一方法です。

`package-lock.json` の `dev` で除外されない576エントリーを概査しました。MIT等に加えて、Apache-2.0、CC-BY-4.0、MPL-2.0、Python-2.0、デュアルライセンス等があります。これは実際のアプリ同梱576件という意味ではありません。たとえばlightningcssやcaniuse-liteはビルド工程で使われるため、配布対象との対応付けが必要です。`node-forge` のBSD／GPL選択肢を理由に、アプリ全体がGPLになると断定していません。

今回の確認はnpmのメタデータと代表的LICENSEまでです。ネイティブのPod／Gradle推移依存、配布物の通知同梱状況はリリースビルドで追加確認します。npmパッケージをインストールできることだけで、配布条件を確認したとは扱いません。

## 7. 不要な権限

Expo SDK 57の `config --type introspect --json` を実行し、Androidの `RECORD_AUDIO` とiOSの `NSMicrophoneUsageDescription` の出力を確認しました。`expo-camera` の `recordAudioAndroid: false` だけでは、`expo-image-picker` が追加する録音権限は消えていません。

アプリコードは静止画とバーコードを扱い、音声録音処理は見つかりませんでした。マイクが既に録音されているとの指摘ではありません。不要な権限・説明を両プラグインで無効にし、配布用Manifest／Info.plistを再確認する項目です。[Expo ImagePicker v57](https://docs.expo.dev/versions/v57.0.0/sdk/imagepicker/)、[Google権限ポリシー](https://support.google.com/googleplay/android-developer/answer/16558241?hl=ja)

生成設定には開発用オーバーレイや旧Android向け保存領域の権限も含まれます。最終ビルドを確認せず、それらがストア配布版にも残ると断定していません。写真ライブラリ全体へのアクセスが必要か、OSの写真選択機能で足りるかも見直します。

## 8. 削除と保持の説明

`FoodDetailScreen.tsx` は「登録データを完全に削除」と表示します。一方、`deleteFood` が削除するのは現行の食材配列で、復元時の旧世代・original退避は `storage.ts` に残り、その参照写真も回収から保護されます。端末の商品候補も別保存です。

復旧を可能にする設計自体は問題ではありませんが、「端末からすべて消える」と受け取られる表示やポリシーは不正確です。現行一覧からの削除と退避データの消去を分け、保持期間・写真の扱い・全データ削除の方法を整えます。外部へ書き出したバックアップをアプリから消せないことも明記します。
