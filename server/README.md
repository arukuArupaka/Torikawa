# 共有商品データベース

公開先を固定しない、Node.js 24.19以降 + SQLite の独立したAPIです。現段階ではローカルで動かし、公開URLが決まったらアプリの接続先を設定します。

## 共有範囲と画面の流れ

- 外部検索でも見つからなかったJAN/EAN商品を手入力したとき、共有のチェック項目を表示します。初期状態はオフです。
- 送信前に、バーコード・商品名・レシピ用分類・カテゴリの4項目を確認できます。
- 禁止内容・利用目的を示す投稿ルールに、その都度同意した場合だけ送信します。投稿は審査待ちで保存し、管理者の承認後に検索できます。
- 在庫、数量、単位、期限、購入日、保存場所、メモ、写真、タグ、利用者IDは共有しません。APIも余分なフィールドを拒否します。商品名や分類にも個人情報を入力しないでください。
- 個人の食材は従来どおり端末内に保存します。共有の通信失敗時には完了画面から商品情報だけを再送できます。自動送信キューはありません。
- 検索順は、端末で学習した商品 → サンプル → 共有DB → Yahoo!ショッピング → Open Food Facts。共有APIの障害時も外部検索へ進みます。
- 共有商品を利用する人の保存場所や数量・期限は、その人の登録画面で決定します。投稿者の設定は引き継ぎません。
- 共有対象はチェックデジットが正しい8桁・13桁のJAN/EANです。2で始まる店舗用コードやUPC-Eなどは対象外です。外部サービスで取得した情報の再投稿も行いません。

## ローカルで動かす（PowerShell）

リポジトリ直下で実行します。APIには追加のnpmパッケージは不要です。

```powershell
npm run shared-api
```

別のターミナルで、`.env.local` に次を設定してExpoを起動してください。既存ファイルがあればこの項目のみを追加・変更します。

```dotenv
EXPO_PUBLIC_SHARED_PRODUCTS_URL=http://127.0.0.1:8787
```

```powershell
npm run web
```

APIは初期状態で同じPCからのみ接続できます。DBは `server/data/products.sqlite` に自動作成し、再起動後も残ります。このフォルダーと `.env.local` はGit対象外です。URL未設定でも食材登録・従来の商品検索は動作します。

スマートフォン上のlocalhostはスマートフォン自身です。実機から利用するときは、信頼できるHTTPSのAPIを設定してください。アプリはローカルホスト以外の平文HTTP接続を許可しません。

## 公開先が決まったら

Node.js 24.19以降の実行環境に `server/` と `shared/` を配置し、`node server/start.cjs` をリポジトリ直下相当のディレクトリから起動します。データベース用の永続ディスクを用意してください。アプリとは別に配置できます。

| 環境変数 | 初期値 | 用途 |
| --- | --- | --- |
| `SHARED_HOST` | `127.0.0.1` | API待受先。コンテナで必要な場合は `0.0.0.0` |
| `SHARED_PORT` | `8787` | APIポート |
| `SHARED_DB_PATH` | `server/data/products.sqlite` | 永続ディスク上のSQLiteファイル。絶対パス推奨 |
| `SHARED_ALLOWED_ORIGINS` | `http://localhost:8081,http://127.0.0.1:8081` | 許可するWebアプリのオリジン。カンマ区切り、ワイルドカードなし |
| `EXPO_PUBLIC_SHARED_PRODUCTS_URL` | 未設定 | アプリに埋め込むHTTPSのAPIベースURL |

APIの前段でHTTPS終端とアクセス制限を設定し、Webアプリの実際のオリジンを許可します。アプリ側の環境変数を変更したらExpoを再起動し、配布アプリは再ビルド・再配布してください。`EXPO_PUBLIC_` の値は公開されるため、DBの認証情報や秘密鍵は入れません。

## API

`POST /v1/products` に `Content-Type: application/json` と `X-Shared-Rules-Version: 2026-10-01` で送信します。ヘッダーは画面に表示した現在の投稿ルールへの同意を示します。本文は次の4項目だけです。ルールの版を変える場合は、表示・クライアント・サーバーを同時に更新してください。

```json
{
  "barcode": "4901234567887",
  "name": "共有テスト牛乳",
  "ingredientName": "牛乳",
  "category": "dairy"
}
```

商品名は120文字以内、分類は60文字以内。改行・制御文字は不可です。カテゴリは `vegetables`, `meat`, `seafood`, `dairy`, `eggs`, `staples`, `seasonings`, `beverages`, `other` のいずれかです。

| 応答 | 意味 |
| --- | --- |
| 201 `pending` | 新規投稿を審査待ちで保存。まだ検索に出ない |
| 200 `already_pending` | 同じ4項目が審査待ちで保存済み。重複しない |
| 200 `already_shared` | 同じ4項目が承認・公開済み |
| 409 `already_exists` | 同じバーコードの内容が異なる、非表示、または却下済み。上書きしない |
| 428 `rules_required` | 現在のルールの版への同意がない。保存しない |
| 400 / 413 / 415 | 不正データ / 2KB超過 / JSON以外 |
| 429 | 投稿・検索の回数制限 |
| 503 `catalog_full` | 保存上限 |

`GET /v1/products/:barcode` は承認済みかつ非表示でない商品の `{ "product": { ...4項目 } }` を返します。未登録・審査待ち・却下・非表示はすべて404です。審査状態・同意記録・通報内容を公開APIへ返しません。`GET /health` は稼働確認用です。

`POST /v1/products/:barcode/reports` は公開中の商品に対し、JSONで `{ "reason": "incorrect" }` を送ります。理由は `incorrect`（誤情報）、`personal_information`（個人情報）、`inappropriate`（不適切な内容）、`rights`（権利侵害の疑い）の4つです。自由記述や余分な項目は拒否します。受付は202 `report_received`、非公開商品は404、理由不正は400。通報にも投稿と共通の回数制限を適用します。

通報は商品・理由ごとに集計し、件数・初回／最終受付・対応日時を保持します。同じ人の再送を判別するIDは保存しないため、件数は通報人数を示しません。悪用による自動非表示を避け、管理者が確認して対応します。利用者は共有情報を使わずに手入力できます。

## 既存DBとアプリの更新

APIの更新前に、停止してDB一式をバックアップしてください。初回起動時の追加列・通報テーブルの作成はトランザクション内で行います。旧商品は内容・作成日時・非表示設定を保持したまま、すべて審査待ちになります。過去の同意は推測して記録せず、ルールの版はNULLのままです。旧商品を公開する場合も内容と権利を個別に確認してください。

APIとアプリを揃えて更新してください。旧アプリは同意ヘッダーを送らないので、新APIへの投稿は428になります。アプリ内の食材登録は残り、共有だけ失敗します。旧APIの即時公開を使い続けながら新アプリだけ配布しないでください。

## 管理・運用

匿名投稿を受け付ける単一インスタンス向けです。投稿ルールへの同意、事前審査、通報、承認・却下・非表示・対応済み記録を実装しています。投稿者の本人確認・個別ブロック・信用評価・自動内容審査は含めていません。CORSや同意ヘッダーは認証の代わりにはなりません。公開には、連絡先、審査と通報への対応担当・頻度・期限、悪用者への措置、保持期間とログ管理を別途決める必要があります。ストア規定への適合をこの実装だけで確定していません。

APIは接続元ごとに投稿20回/時、検索300回/分、最大5万商品に制限します。IPはソルト付きハッシュをプロセス内の短期カウンターにだけ使用し、DBやアプリログには保存しません。カウンターは再起動でリセットされます。リバースプロキシ経由では接続元が共通になるため、前段でも適切な制限を設定してください。`X-Forwarded-For` は信用しません。ホスティング側のアクセスログは別途設定が必要です。

サーバー管理権限のある端末から操作します。同じ `SHARED_DB_PATH` を指定してください。公開の管理APIはありません。一覧は最大100件です。大量の確認や内容訂正はバックアップ後にDBを整備する運用です。

```powershell
node server/admin.cjs list
node server/admin.cjs approve 4901234567887
node server/admin.cjs reject 4901234567887
node server/admin.cjs reports
node server/admin.cjs hide 4901234567887
node server/admin.cjs resolve 4901234567887
node server/admin.cjs restore 4901234567887
```

`list` は審査待ち、`list approved|rejected|hidden` は指定状態の一覧です。`reports` は未対応、`reports resolved` は対応済みの通報です。`resolve` はその商品の現在の通報を対応済みにするだけで、商品を非表示にしません。必要なら先に `hide` を実行します。新しい通報を受けると再び未対応になります。

`approve` は内容の承認で、以前の `hide` は解除しません。`restore` は承認済み商品の非表示解除だけです。審査待ち・却下商品の公開には明示的な `approve` が必要です。非表示・却下商品を再投稿しても復活しません。既存商品を変更・削除する公開APIはありません。

DBのバックアップはAPIを停止してから `products.sqlite` と残っている `-wal` / `-shm` を一式保存してください。稼働中に本体ファイルだけコピーしないでください。複数インスタンスに拡張する場合は共有DBへの移行と投稿制限の共通化が必要です。

## 検証

```powershell
npm test
npm run typecheck
```

テストは一時DBで、同意なしの拒否、承認前の参照拒否、旧DBの移行、別クライアントからの承認後の参照、再起動後の永続性、通報の集計・対応・非表示、個人項目の拒否、重複投稿、通信障害時のフォールバック、再試行時の食材重複防止を確認します。テストデータを運用DBへ流し込む必要はありません。
